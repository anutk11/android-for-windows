# הוראות עבודה לבודקים שעורכים קוד

מסמך זה הוא **טיוטה להערות**. עד שכל הבודקים והמחבר הראשי יסכימו עליו, לא עורכים קוד: רק כותבים הערות (Issue בשם `COLLABORATION: <הערה>` או תגובה על השורה ב-PR).

## למה עבודה מקבילה בכלל אפשרית

ליבת הטוען (patch, ELF, TLS) מתקדמת שלב אחרי שלב, וכל שלב תלוי בקודם. אבל יש מודולים שיש להם ממשק קבוע ובדיקה משלהם, ואפשר לכתוב אותם במקביל בלי לחכות. רק אותם מחלקים.

## כללים

1. **אין דחיפה ל-main.** כל שינוי נעשה בענף `review/<שם>-<נושא>` ונכנס דרך PR.
2. **PR נכנס רק כש-CI ירוק בכל החלקים**, כולל `linux-asan`, ואחרי שבודק אחר אישר אותו. בודק 3 לא יכול לאשר PR ישירות. כשמבקשים ממנו ביקורת, האישור שלו מועבר ונרשם בתגובה ב-PR.
2א. **אישור תקף רק ל-commit האחרון.** דחיפה חדשה ל-PR מבטלת אישור קודם.
2ב. **מי בודק את מי:** PR של המחבר הראשי נבדק על ידי בודק 1, בודק 2 או בודק 4. PR של בודק 1 נבדק על ידי בודק 2. PR של בודק 2 נבדק על ידי בודק 1 או בודק 4. PR של בודק 4 נבדק על ידי בודק 2. בודק שנעדר לא מעכב PR שבודק אחר כבר אישר, חוץ משינוי שער לפי כלל 6. הבודק מוודא ארבעה דברים: שהבדיקה נכשלת בלי השינוי (כלל 4), שאין החלשה של שער (כלל 6), גלישות אורך ובדיקת כישלון בכל קריאת מערכת (כלל 8), ושלא נכנס קובץ מתמונת Android (כלל 5).
3. **לא נוגעים בקבצים של תחום אחר.** אם צריך שינוי שם, פותחים Issue ומתארים מה צריך ולמה.
4. **כל קוד חדש מגיע עם בדיקה שנכשלת בלעדיו.** בדיקה שעוברת גם בלי השינוי לא נחשבת.
5. **אסור להעלות קבצים מתמונת Android** (libc.so, linker64 וכו'), גם לא בענף. הם נשלפים רק בתוך CI, ורק דוחות עולים.
6. **אין החלשה של השער.** שינוי שמוריד בדיקה, מוסיף `--allow-unproven` ב-CI, או משנה ציפייה בשער (`GATE ... would RUN/REFUSE`) צריך הסכמה מפורשת של כל השלושה, בכתב ב-PR.
7. **בדוחות, כל טענה מסומנת "נמדד"** עם הפניה לפלט CI, **או "השערה"**. דוח בלי הסימון הזה לא נחשב.
7א. **עובדה נמדדת מנצחת דעה.** במחלוקת כותבים ניסוי קטן שמכריע, כמו שנעשה ב-WRFSBASE וב-mprotect(PROT_NONE).
8. **קוד C:** C11. מחוץ ל-`src/platform.c` אין קריאה ישירה ל-Win32. כל פונקציה שקוראת למערכת ההפעלה מחזירה הצלחה או כישלון, ואין שינוי במטא-דאטה לפני הצלחה. כל חישוב אורך נבדק לגלישה.

## דרישות לאורקל `libc_shared_globals` (הוצע ב-Issue #1, אושר על ידי המחבר הראשי)

1. **מקור נעול.** `UE1A.230829.036.A1` הוא מספר build של התמונה, לא תג AOSP. ה-libc מגיעה מ-APEX של runtime, שיכול להתעדכן בנפרד מהתמונה. לכן מוודאים את ההתאמה מול `build.prop`, מול גרסת ה-APEX ומול manifest התג, ורושמים את הנימוק. ה-Build ID לבדו לא מספיק.
    commit מדויק של `platform/bionic`, וכל מאגר נוסף שהכותרות תלויות בו. הנתיב וה-hash של כל קובץ כותרת נרשמים ב-`tools/oracle/SOURCE.lock`. הגרסה נבחרת כך שתתאים לתמונה שנמדדה (`UE1A.230829.036.A1`, Build ID של libc `fa337969c798946280caa45e2d71a2e7`). את ההתאמה בודקים, לא מניחים.
2. **הכותרות האמיתיות.** האורקל כולל את `private/bionic_globals.h` מתוך המקור הנעול. מותר להוסיף קבצי עזר (shim) רק לתלויות שלא קשורות לפריסה, ורק כשכל אחד מהם מתועד. אסור להעתיק את המבנה עצמו.
3. **פלט קבוע.** שורת `key=value` לכל מאפיין: `sizeof`, `alignof`, ולכל שדה `offsetof` ו-`sizeof`. גם מבנים מקוננים נפרשים שדה אחר שדה.
4. **שני צדי ה-ABI.**
   - הייחוס נבנה ב-NDK עבור `x86_64-linux-android`.
   - הצד שלנו הוא כותרת עם טיפוסים ברוחב קבוע בלבד, `src/bionic_abi/shared_globals.h`, באחריות המחבר הראשי. הוא נבנה ב-clang-cl על Windows x64.
   - ה-CI משווה את שני הצדדים, ונכשל גם על שדה חסר או שדה עודף.
5. **מה שלא נמדד ישירות** (למשל bit-field) מתועד בנפרד, עם בדיקה חלופית. אין ניחוש של offset.
6. **בדיקה שלילית.** ב-CI מזיזים שדה אחד ומחליפים טיפוס אחד בעותק של הכותרת שלנו. ההשוואה חייבת להיכשל בשני המקרים.
7. **מה עולה:** רק נתוני פריסה וקוד. לא עולים קבצים מתמונת Android. האורקל מוכיח פריסה בלבד, לא סמנטיקה ולא אתחול נכון.
8. **README קצר:** מקור, ABI, הוראות בנייה, ומה הבדיקה לא מוכיחה.

## נתונים לדוח ה-UNPROVEN

ה-CI (חלק `bionic-probe`) מפיק את `unproven-scan.txt` בתוך הארטיפקט `bionic-scan-report`. לכל אתר יש בו:
- ה-offset בספרייה.
- טווח הפונקציה, וכמה מהבתים שלה הניתוח הגיע אליהם.
- הקפיצה העקיפה שהשאירה את הפונקציה בלי הכרעה.
- 32 בתים סביב האתר.
- פענוח לינארי של הפונקציה סביב האתר, כשכל פקודה מסומנת R (הניתוח הגיע אליה) או - (לא הגיע).

ה-CI גם בודק שמספר האתרים הוא בדיוק 9.

## איך מגישים

```
git checkout -b review/<name>-<topic>
# שינוי + בדיקה
git push -u origin review/<name>-<topic>
gh pr create --fill
```

בתיאור ה-PR כותבים מה השתנה, איזו בדיקה מוכיחה את השינוי, ומה עלול להישבר.
